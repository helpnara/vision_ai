# 작업 진행 규약 — 설계 → 개발 → 검증

> 만든 날: 2026-11-09 (다른 계정으로 이관하면서)

세션이 끊기거나 계정이 바뀌어도 **어느 항목이 어느 단계에 있는지**가 저장소만 보고 드러나게 하려고 만든
규약이다. 항목 하나를 세 단계로 나누고, 단계마다 **남기는 것**과 **끝났다고 말할 기준**을 정해 둔다.

* 남은 항목과 지금 단계 → [`todo.md`](todo.md) «지금 열려 있는 항목» 표의 **단계** 열 (단일 출처)
* 항목별 설계·변경 기록·검증 결과 → `docs/plans/<ID>-<짧은이름>.md` (틀: [`plans/TEMPLATE.md`](plans/TEMPLATE.md))
* 함정 규칙·명령·브랜치 → [`../CLAUDE.md`](../CLAUDE.md)

---

## 한눈에

| 단계 | 하는 일 | 남기는 것 | 끝났다는 기준 | 커밋 제목 |
|---|---|---|---|---|
| **설계** | 범위·바뀌는 파일·API/화면 변화·검증 계획을 문서로 | `docs/plans/<ID>-….md` (설계 절까지) | **사용자가 승인했다** | `<ID> 설계: <무엇을 하려는가>` |
| **개발** | 설계대로 코드와 테스트를 함께 짠다 | 코드 · 테스트 · (화면이면) `web/dist` · 설계 문서 «변경 기록» | 설계 문서의 «검증 계획» 테스트가 전부 있고 통과 | `<ID>: <사용자가 얻는 것>` |
| **검증** | 아래 체크리스트를 돌리고 숫자를 남긴다 | 설계 문서 «검증 결과» · todo 체크 · HANDOFF 갱신 | 체크리스트 전부 ✅, 배포 브랜치 반영 | `<ID> 검증: <결과 한 줄>` |

단계가 바뀔 때마다 todo 표의 **단계** 열을 같은 커밋에서 고친다. 그것만 보면 다음 세션이 어디서
이어야 하는지 안다.

---

## 1. 설계

1. `docs/plans/TEMPLATE.md`를 `docs/plans/<ID>-<짧은이름>.md`로 복사해 «목적 · 범위 · 하지 않는 것 ·
   바뀌는 곳 · 함정 규칙 점검 · 검증 계획 · 열린 질문»을 채운다.
2. **코드를 읽고 쓴다.** 추측으로 쓴 «바뀌는 곳»은 개발 단계에서 거의 틀린다. 파일·함수 이름까지 적는다.
3. **검증 계획에 테스트 이름을 미리 적는다.** 새 지표·차트·영상 출력이면 CLAUDE.md 함정 규칙의 회귀
   테스트(«전부 결함» 입력, 높이 실측, 한글 글리프, WebM, Windows 가짜)를 여기서 고른다.
4. 열린 질문이 남아 있으면 **사용자에게 묻고 답을 문서에 적은 뒤** 승인을 받는다.
5. 설계 문서만 커밋한다(코드 없음). todo 단계 열 → `설계`.

> **승인 없이 개발로 넘어가지 않는다.** 이 단계의 존재 이유는 «만들고 나서 방향이 틀린 걸 아는 일»을
> 줄이는 것이다.

## 2. 개발

1. todo 단계 열 → `개발`.
2. 설계의 «검증 계획» 테스트부터 쓰거나 코드와 함께 쓴다. **코어(`src/vision_ai/`)는 화면을 모른다**는
   구조 규칙을 지킨다.
3. 화면(`web/src`)을 고쳤으면 `npm run build` 결과(`web/dist`)를 **같은 커밋**에 넣는다.
4. API를 새로 넣었으면 `tests/test_api_<화면>.py`에 배선 테스트, 응답은 `common.jsonable/table/records`로.
5. **설계에서 벗어나면 설계 문서 «변경 기록»에 왜 벗어났는지 적는다.** 설계 문서가 실제와 어긋난 채로
   남으면 다음 세션이 틀린 지도를 들고 시작한다.
6. 커밋은 항목 하나 = 커밋 하나가 원칙이다. 크면 설계 문서에 나눈 조각(«개발 조각») 단위로 나눈다.

## 3. 검증

`python scripts/verify.py`가 1~4를 한 번에 돌린다(화면을 고쳤으면 `--web`).

| # | 확인 | 기준 |
|---|---|---|
| 1 | `python -m pytest -q` | 전부 통과. passed 수는 **기준(CLAUDE.md)보다 늘었거나 같다** — 새 테스트만큼 늘어야 한다 |
| 2 | `ruff check .` | **9건 그대로** (늘면 새로 건드린 파일 탓) |
| 3 | 앱 기동 | `/api/health` → `{"ok":true,…}`, `/` 200 |
| 4 | (화면) `npm run build` | 통과하고, 다시 빌드해도 `web/dist`에 차이 없음(커밋된 dist가 소스와 맞음) |
| 5 | (화면) Playwright 스크린샷 | 바뀐 화면을 **눈으로** 본다. 콘솔 오류 0. 좁은 폭(390px)도 한 장 |
| 6 | 함정 규칙 회귀 | 설계 «함정 규칙 점검»에서 해당한다고 한 것의 테스트가 통과 |
| 7 | 사용자 확인 | 사용자가 PC에서 봐야 하는 변화면 배포 zip을 만들고(`scripts/package_release.py`) 확인을 받는다 |

끝나면:

* 설계 문서 «검증 결과»에 **숫자로** 적는다 (예: `812 passed · 4 skipped`, 린트 9, 스크린샷 파일 이름).
* `todo.md`의 체크박스를 닫고 «지금 열려 있는 항목» 표에서 뺀다. CLAUDE.md의 테스트 기준 수를 갱신한다.
* `HANDOFF.md`의 «지금 상태»를 갱신한다.
* 작업 브랜치에 푸시 → 배포 브랜치로 fast-forward (CLAUDE.md «작업 습관»).

---

## 4. 항목 ID

기존 결을 따른다 — `V5`·`H`·`E`처럼 todo.md 절 이름이 곧 ID다. 이관 뒤 새로 연 «전환 뒤 다듬기»는
**`R1`~`R7`**(Refine)로 부른다. 새 절을 열면 todo.md에 절을 먼저 만들고 그 글자를 쓴다.
