## V. 다른 영상으로 탐지율을 재는 경로 (활용 관점)

**하려는 일**: 영상 A에서 프레임을 뽑아 라벨링하고 모델을 만들었다. 이제 **영상 B(다른 CCTV
영상)** 를 넣어 이 모델이 얼마나 탐지하는지 재고 싶다.

### 이미 되는 것 (다시 만들지 말 것)

코드를 짚어 확인했다.

- 영상 B에서 프레임 추출 → manifest 등록. 영상 id가 `group` 열에 붙는다.
- **구간 라벨링으로 붙인 정답이 성능 측정에 그대로 쓰인다.** `resolve()`가 이 라벨을
  `label_source=human` · `verified=True`로 남기고, `monitoring.feedback_frame()`이 정답으로
  인정하는 조건이 바로 그것이다 — 폴더 추론 라벨은 자기 채점이라 배제된다.
- 4단계 배치 추론 → 판정 로그 → **성능 추이**에서 재현율·정밀도·미탐·오탐이 나오고,
  등록 시점 대비 낙폭이 0.05를 넘으면 경고까지 뜬다.
- **드리프트 감시가 영상 간 차이를 잡는다.** 학습 입력 분포와 지금 들어온 입력을 비교하므로,
  영상 B의 각도·조명이 다르면 여기서 먼저 드러난다. 성능 하락의 원인이 모델인지 촬영인지
  가르는 근거가 된다.

즉 **뼈대는 이미 있다.** 아래는 그 뼈대를 "영상 단위"로 쓸 수 있게 만드는 일이다.

### 검출인가 이상탐지인가 — 그보다 **화각이 먼저다**

지금 프로젝트에 쌓인 **실제 결함 박스 1,334개**로 재 봤다 (VisA 원본 약 1400×1000).

| | 박스 짧은 변 | 화면 폭 대비 |
|---|---|---|
| 하위 25% | 10px | 0.78% |
| **중앙값** | **23px** | **1.78%** |
| 상위 25% | 54px | 4.30% |

**표면 결함은 화면에서 폭의 2% 남짓이다.** 이 크기를 CCTV 화각에 넣으면:

| 카메라가 담는 폭 | 중앙 결함 | 하위 25% 결함 |
|---|---|---|
| 0.3m (근접 촬영) | 34px | 15px |
| 1.0m (컨베이어 한 줄) | 10px | 5px |
| 3.0m (라인 전체) | **3px** | 2px |
| 10m (공장 전경) | 1px | 0px |

1920px 카메라 기준이다. **넓게 보는 고정 카메라라면 어떤 모델을 써도 안 잡힌다** — 결함이
3픽셀이면 사람도 못 본다. 모델 선택보다 이것이 먼저다.

기준선: YOLO는 640px로 줄여 학습하므로 결함이 **화면 폭의 3% 이상**이어야 입력에서 20px가
되어 안정적으로 잡힌다. **1.5% 미만이면 사실상 불가능**하다. 이미 `video.plan_from_process()`가
"이 촬영으로는 목표 장수를 못 채운다"를 미리 알려주는 것과 같은 성격의 점검이다.

- [x] **V0 촬영 화각 점검** — 1단계 영상 탭의 **추출 버튼 위에** 넣었다(`framing.py`).
      결함 실물 크기(mm)·카메라가 담는 폭(m)·모델 입력 크기·타일 등분 수를 받아
      «원본에서 N px → 모델 입력에서 M px → 가능/어려움/불가»를 판정하고, 안 되면
      **무엇을 바꾸면 되는지 비용이 싼 순서로** 알려준다.
      가장 쓸모 있는 값은 «이 촬영으로 잡을 수 있는 가장 작은 결함(mm)»이다 — 결함 크기는
      알아도 그래서 되는지는 모르는 것이 보통이라, 그 숫자와 비교하면 바로 답이 나온다.
      **핵심은 소프트웨어로 못 넘는 벽을 못 넘는다고 말하는 것이다.** 원본이 이미 20px를
      못 담고 있으면 타일 분할도 입력 크기도 소용없고, 그런 지렛대는 «원본에 그만한 정보가
      없어 소용없습니다»로 지워서 보여준다. 이걸 놓치면 "잘게 자르면 다 잡힌다"는 거짓
      결론이 나오고 사람은 안 되는 촬영으로 며칠을 쓴다.

### 그 위에서 — 검출로 간다

화각이 받쳐 준다는 전제에서, **CCTV 입력이면 검출(YOLO)이 맞다.**

- **이상탐지는 "정상과 다른 것"을 전부 이상이라 부른다.** CCTV는 정상 자체가 계속 변한다 —
  시간대별 조명, 그림자, 사람·지게차 통과, 렌즈 오염. 그 변화가 전부 결함으로 신고된다.
- 근거는 이 프로젝트 안에 있다. VisA는 **고정 조명·고정 각도의 스튜디오 촬영**인데도
  이상탐지 오탐률이 45.5%다. 정상이 거의 안 흔들리는 최상의 조건에서 그 숫자다.
  드리프트 실측에서도 기준선 평균 72.68 vs 현재 72.60으로 **사실상 같은 입력**인데
  PSI 0.2085로 «주의»가 떴다 — 이 접근은 조금만 흔들려도 반응한다.
- 검출은 배경을 배경으로 **배운다.** 사람이 지나가도 스크래치라고 하지 않는다.

**다만 순서가 있다.** 처음에는 결함 박스가 없으므로 이상탐지로 후보를 뽑아 사람이 확인하고,
그렇게 박스가 쌓이면 검출로 갈아탄다. 이 앱이 이미 그 흐름이고, 마스크 자동 생성으로
**447장·박스 1,393개**를 확보해 검출로 넘어갈 재료는 생겼다.

> 이상탐지를 버리지는 않는다. **처음 보는 결함 유형**은 검출이 못 잡고 이상탐지가 잡는다.
> 둘을 함께 두고 이상탐지는 «못 보던 것» 경보로 남기는 것이 현장의 보통 구성이다.

### 단계별 개선

앞 단계가 뒤 단계의 전제라 순서를 지켜야 한다. V1이 없으면 V2~V4가 성립하지 않는다.

- [x] **V1 추론 로그에 영상 id를 남긴다** — `INFERENCE_COLUMNS`에 `group`을 넣고
      `run_batch()`가 채우게 했다. 실측으로 영상 프레임 8장을 판정해 로그에서
      `checkpoint-507797e6` 8행만 갈라내는 것까지 확인했다.
      **가장 조심한 것은 기존 로그를 깨뜨리지 않는 일이다.** 로그는 헤더 없이 이어 붙이므로
      열이 하나 늘어난 채로 그냥 붙이면 줄마다 칸 수가 달라져 **파일 전체를 못 읽게 된다**
      — 예전 판정 이력이 통째로 날아간다. 붙이기 전에 다시 쓰는 마이그레이션을 넣고
      실제 로그 168행이 그대로 남는 것을 확인했다. 우리가 모르는 열이 있는 파일은
      **건드리지 않는다** — 열을 맞추려다 남의 것을 잃는 편이 더 나쁘다.
- [x] **V2 배치 추론 대상에 «영상» 선택을 넣는다** — 선택지에 «영상 하나»를 더하고 영상별
      프레임 수를 함께 보여준다. 실측으로 영상 36장을 판정해 **그 영상만의 재현율 1.0
      (13건 중 13건)** 을 냈다 — V1+V2의 목적이 바로 이것이다.
      **앞에서부터 자르지 않고 고르게 뽑는다**(`labeling.even_sample`). 10분 영상의 앞
      200장은 앞 2분이고, 조명이 바뀌거나 물건이 달라지는 뒷부분이 통째로 빠지는데 그
      사실이 지표에는 안 드러난다 — 그냥 «재현율 0.9»로 보인다.
      정답 라벨이 없는 영상을 고르면 «판정은 되지만 얼마나 맞았는지는 알 수 없다»고 미리
      알려주고 구간 라벨링으로 안내한다.
- [x] **V3 영상·구간 단위 검출률** — 4단계 **성능 추이**에 «영상·구간 단위 검출률»을
      넣었다(`segments.py`). 구간 하나를 한 건으로 세는 **구간 재현율**과, 정답 구간과 한
      곳도 겹치지 않은 알람을 **분당 횟수**로 낸 오경보율을 프레임 지표와 나란히 놓는다.

      **실측이 이 항목의 존재 이유를 그대로 보여 줬다.** 합성 라인 영상(24초·72프레임·정답
      구간 3곳)에 이상탐지 모델을 걸고 임계값만 올려 가며 재 봤다:

      | 임계값 | 프레임 재현율 | 구간 재현율 | 헛알람 |
      |---|---|---|---|
      | 4.0 | 1.00 | 1.00 | 2건 (분당 5.1회) |
      | 12.0 | 0.77 | 1.00 | 0 |
      | 16.0 | 0.55 | 1.00 | 0 |
      | 20.0 | **0.23** | **1.00** | **0** |

      임계값 20에서 프레임 숫자만 보면 «재현율 0.23, 못 쓴다»가 된다. 그런데 **결함 구간
      3곳을 모두 잡았고 헛알람은 0건**이다 — 현장 기준으로는 오히려 가장 좋은 운영점이다.
      프레임 지표만 들고 갔으면 쓸 만한 모델을 버릴 뻔했다.

      두 숫자가 크게 벌어지면 화면이 **그 사실을 말로 알려 준다**(`contrast()`). 숫자만
      나란히 두면 어느 쪽을 믿을지 모른다.
      «몇 장을 잡아야 잡은 것으로 볼지»(기본 1장)는 화면에서 올릴 수 있다 — 사람이 확인하러
      가는 비용이 큰 현장이면 «한 장은 튄 것일 수 있다»를 반영해야 한다.
      가장 조심한 것은 **영상 순서로 다시 세우는 일**이다. 로그는 판정한 순서대로 쌓이고 그
      순서는 영상 순서가 아니다. 어긋난 채로 «이어짐»을 따지면 한 구간이 여러 조각으로
      부서져 오경보율이 실제보다 크게 나온다.
- [ ] **V4 «학습 영상 vs 평가 영상» 비교 리포트** — 지금은 성능(성능 추이)과 입력 분포
      변화(드리프트)가 다른 탭에 흩어져 있다. 다른 CCTV로 옮겨 갈 때 알고 싶은 것은
      **"성능이 떨어졌다면 모델 탓인가 촬영 탓인가"** 하나이므로, 두 영상의 지표와 PSI를
      한 화면에 나란히 놓고 결론 문장을 붙인다. 판단 근거는 이미 다 있고 모으기만 하면 된다.
- [ ] **V5 검출 모델(YOLO)로 새 영상을 판정하는 경로** — 지금 앱의 4단계 추론은
      **이상탐지·분류 모델만** 태울 수 있다(`serving.load_version()`이 아는 종류가 그 둘뿐).
      `scripts/train_detector.py`로 만든 `best.pt`를 다시 앱으로 들여 영상 B를 판정하는
      통로가 없다. 검출 모델까지 쓸 계획이면 이 단계가 필요하다 — 다만 ultralytics 의존과
      GPU가 얽히므로 **V1~V4를 이상탐지 모델로 먼저 완성한 뒤** 붙이는 편이 낫다.
- [x] **V7 판정 결과를 영상으로 되돌려 재생** — 4단계에 «🎥 판정 영상» 탭을 넣었다
      (`playback.py`). 영상을 고르고 버전을 고르면 프레임마다 판정을 그려 넣은 재생본을
      만들어 **영상이 위, 대표 판정 결과가 아래**로 놓인다. 실측으로 360프레임짜리를 120장
      판정해 12초짜리 재생본을 만들었고, 브라우저가 실제로 디코딩하는 것(1284×480 / 12초)까지
      확인했다.
      **이상탐지 모델이면 왼쪽에 박스, 오른쪽에 열지도를 나란히** 놓는다 — 박스만 보면 «왜
      저기냐»를 알 수 없고, 열지도만 보면 «잡았다/놓쳤다»가 안 보인다. 분류 모델은 결함의
      위치를 모르므로 박스 없이 판정 띠만 얹는다(없는 정보를 지어내지 않는다).
      원본은 건드리지 않고 **판정본을 따로** 만든다. 영상×버전마다 폴더를 갈라 두어 «어느
      모델이 잡은 것인가»를 비교할 수 있다.

      만들면서 실측으로 뒤집힌 것 셋:
      1. **브라우저가 재생할 수 있는 코덱이 하나뿐이다.** 이 OpenCV 빌드에는 H.264 인코더가
         없고, 있는 `mp4v`는 크롬·파이어폭스가 재생하지 못한다(파일은 멀쩡히 만들어진다 —
         그래서 «만들었는데 안 보인다»로 나타난다). WebM/VP8로 쓴다. 그마저 안 되는 환경을
         위해 대비책을 두되 그때는 «내려받아 보라»고 말해 준다.
      2. **CJK 글꼴이라고 한글이 나오지 않는다.** 이 환경의 일본어 고딕은 한자는 그리는데
         한글 자리에는 네모를 찍는다. 파일 존재만 확인하면 네모가 줄줄이 박힌 영상을 만들고
         나서야 알게 되므로, 쓰기 전에 «없는 글자»와 같은 모양인지 대 본다
         (`viz.draws_hangul`). 한글 글꼴이 하나도 없으면 영문으로 대체해 그린다.
      3. **열지도 색을 프레임마다 정규화하면 안 된다.** 정상 프레임의 미세한 얼룩이 결함과
         똑같이 새빨개져서 재생 내내 화면이 요동친다. 판정 기준선을 색 눈금 한가운데에
         고정하니 «붉으면 기준선 위»가 영상 내내 같은 뜻이 됐다.

      화면을 새로 열면 **이미 만들어 둔 판정본을 되찾아 온다** — 몇 분짜리 작업을 매번 다시
      시키면 아무도 두 번 쓰지 않는다. 폴더 이름(영상 내용 해시)으로 찾지 않고 안에 적힌
      것을 읽어 맞춘다. 해시를 내려면 위젯 하나 건드릴 때마다 영상 전체를 다시 읽어야 한다.
- [ ] **V6 놓친 곳을 타임라인에서 되짚기** — 미탐이 몇 건인지보다 **영상의 어디서 놓쳤는지**가
      다음에 무엇을 더 라벨링할지 정해 준다. H4의 구간 타임라인 위에 모델 판정을 겹쳐 그리면
      «정답 구간 / 모델이 잡은 구간»이 한눈에 어긋나 보인다. 이미 만든 타임라인을 재사용한다.

### 시작 전에 정해야 할 것

### 이미 목적에 맞게 되어 있는 것 (다시 손대지 말 것)

**운영관리가 된다는 걸 보여줄 방법이 없다.** 이게 이번 검토에서 새로 나온 가장 중요한 문제다.

그런데 지금 시연자가 4단계를 열면 전부 빈 화면이다. 합성 데이터로 배치 추론을 한 번 돌려도
추이가 없어서 "그래프가 하나 찍혔다"로 끝난다. 기능은 다 구현되어 있는데
**작동하는 모습을 보여줄 수가 없다.** 목적이 "운영관리도 가능함을 보여주기"인데 이건 치명적이다.

## A. 운영관리를 시연 가능하게 (최우선 · 이번 검토에서 새로 도출)

- [x] **A1. 운영 시나리오 시뮬레이터** — ✅ 완료 (`src/vision_ai/scenario.py`, 4단계 첫 탭).
      버튼 한 번으로 운영 3개월치를 재생한다.
      기능을 새로 만드는 게 아니라 **이미 만든 4단계 기능이 작동하는 모습을 보이게 하는 것**이다.

      재생 범위: 모델 승격 → 정상 운영(추론 로그 축적) → 조명 변화 주입 → PSI 경고 →
      사후 검수로 성능 변화 확인 → 재학습 신호 발생. **재학습·재승격은 시뮬레이터가 대신하지
      않는다** — 3단계 학습과 레지스트리 승격이라는 실제 기능을 그대로 쓰게 두는 편이
      "운영이 돈다"를 보여주는 데 맞다. 롤백 갈래는 A4로 남긴다.

      드리프트는 밝기/흐림 변환을 `serving.run_batch(transform=...)`에 끼워 주입한다.
      각 구간에서 "지금 무슨 일이 일어났고 왜 이 화면을 봐야 하는지"를 함께 표시한다.

      (결함 판정 비율 6% → 34% → 83%). 원인도 정확히 짚힌다 — 조명 변화는 `gray_mean`,
      초점 저하는 `lap_p99`의 PSI가 튄다. 애초에 써 둔 시나리오 설명("재현율이 떨어진다")은
      측정과 달라 바로잡았다. 이 상황의 실제 피해는 결함을 놓치는 것이 아니라
      **사람이 볼 물량이 감당 불가로 늘어나는 것**이다.

## C. 지표 해석 도움말

앱에 표시되는 지표가 **49종**인데 대부분 숫자만 나온다. 현재 `help=` 도움말은 18개뿐이고
홈 화면에는 하나도 없다. "이 값이 높으면/낮으면 무슨 뜻이고 무엇을 해야 하는지"를 붙인다.

- [x] **C1. 품질 개선 효과를 업무 언어로** — ✅ 완료.
      환산 로직을 `evaluate.business_impact()`로 코어에 모으고 3단계 평가 화면·홈·해석
      스크립트가 **같은 계산**을 쓰게 했다. 화면에서 불량률과 검사 물량을 직접 바꿔볼 수 있다.

      `놓치는 결함` 건수를 항상 나란히 낸다. 둘을 같이 봐야 도입 여부를 판단할 수 있다.
      기대 정밀도가 50% 미만이면 "자동 판정용으로 쓸 수 없다"는 경고를 띄운다.
- [x] **C2. 결과 판정과 다음 행동 제안** — ✅ 완료 (`glossary.verdict()`).

      절감 없음·현장 정밀도 부족을 각각 짚어 다음에 할 일을 문장으로 낸다.
- [x] **C3. 정밀도 오해 방지** — ✅ 완료. 정밀도 캡션에 "평가 데이터 기준이라 현장과

- [x] **C4. 재현율↔정밀도 맞교환** — ✅ 완료. 임계값 조정 설명을 "한쪽만 좋게 만들 수는

- [x] **C5. 지표별 설명** — ✅ 완료 (`glossary.METRICS`, 13개 지표).

### 도움말 배치 방식 (먼저 결정할 것)

| 방식 | 장점 | 단점 |
|---|---|---|
| `?` 아이콘 (`help=`) | 화면이 깔끔 | 눌러야 보여서 초보자는 그냥 지나침 |

**혼합안으로 확정** — 핵심 지표(`primary=True`)는 캡션으로 바로 보이게, 부가 설명은 `?`에 둔다.

(전에는 정밀도가 3단계·홈·문서에서 각각 다른 문장으로 설명되고 있었다.)

## F. 기술 작업 (성능·검증)

목적이 "초보자도 할 수 있음을 보여주기"이므로 **성능 개선보다 A~C가 먼저다.**
지금 성능(평균 AUROC 0.830)으로도 "검수량 54% 절감"이라는 이야기는 성립한다.

- [x] **성능 개선 시도** — 사전학습 CNN 측정 완료(4.6). 소폭 개선이나 위치 정확도가
      나빠져 선택 기능으로만 둔다. 벤치마크 수준(0.95)을 원하면 PatchCore 계열로
      **방법 자체를 바꿔야 한다** — 특징만 갈아끼워서 되는 일이 아니었다.
- [x] **재현율 목표 미달 해소 — 카테고리별 임계값** — 임계값 하나를 전체에 쓰면 **가장 어려운
      카테고리가 전체를 끌어내린다.** 평균 0.925인데 pcb4만 0.840이었던 것이 그 모양이다 —

- [x] **결함 유형 라벨링** — 흐름 확인 및 유형 파악 완료 (설계 문서 4.7).

## G. 사용성 (쓰면서 계속 발굴)

기능이 다 있어도 화면이 불편하면 계속 쓰지 않게 된다. **실제로 써 보다가 걸린 것을 그때그때

- [x] **G1 글자 크기** — 기본 테마는 발표 슬라이드에 가까워서 h1이 44px, 지표 값이 36px였다.

- [x] **G2 여백** — 본문 상단 90px·하단 150px, 구분선 위아래 각 2rem이 스크롤을 한 번 더

- [x] **G3 메뉴 레일 모드** — 기본 사이드바는 접으면 통째로 사라져서 "지금 몇 단계인지"를

- [x] **G12 진행 표시** — 막대만 채우면 화면이 멈춘 것처럼 보여 사람은 새로고침을 누른다.
      **왜 오래 걸리는지**를 먼저 말하고(`이미지 4,584장에서 각각 67개 값을 계산합니다`),
      진행하면서 **남은 시간**을 실측 속도로 갱신한다(`특징 추출 중 100/4,584 · 남은 시간 약 45초`).
      처음 12건은 편차가 커서 값을 못 믿으므로 그전에는 건수만 보여준다. 끝나면 실제로 걸린
      시간을 남긴다(`1분 28초 걸림`).
- [x] **G13 특징 캐시** — 한 번 계산한 특징을 `artifacts/cache/`에 남긴다.
      **이미지 단위**로 남기는 것이 핵심이다 — 집합 단위로 캐싱하면 이미지를 10장 추가하는
      순간 전체가 무효가 되지만, 이미지 단위면 늘어난 10장만 계산한다.
      실측 **144초 → 0.1초** (동일 결과 확인, 캐시 파일 4,584장에 1.0MB).
      파일이 바뀌었거나(수정 시각·크기) 특징 정의가 바뀌면 자동으로 버린다.
      설정 화면에 현황과 비우기를 뒀다.

- [x] **G15 결함 위치를 드래그로 지정** — 결함 위치(ROI)를 x/y/폭/높이 슬라이더 4개로 맞추게
      되어 있었다. 값을 옮길 때마다 그림을 다시 봐야 해서, **보고 있는 것과 조작하는 것이
      떨어져 있었다.** 이미지 위에서 드래그하면 영역이 잡히고, **잡은 영역 안쪽을 끌면 위치가
      옮겨진다**(Vega 기본 동작이라 따로 만들 필요가 없었다).
      **새 의존성 없이** 했다 — `streamlit-drawable-canvas` 같은 컴포넌트를 붙이는 대신
      Streamlit에 이미 들어 있는 Vega-Lite 구간 선택을 썼다. 배포 환경에서 깨질 여지가 없다.
      화면에는 640px로 줄여 그리지만 **좌표는 원본 픽셀**로 나온다(축 도메인을 원본 크기로 둠).
      마스크 자동 추출은 그대로 우선 제안된다.

다음 회차 후보 (아직 손대지 않음):

- [x] **G14 이상탐지 탭의 패치 특징 캐시** — 재 보고 정했다. 실측 1,000장 기준 **42.4초 →
      0.15초 (280배)**, 4,584장 환산 194초 → 0.7초. 이상탐지 탭은 설정을 바꿔 가며 여러 번
      돌리는 화면이라 그 시간을 누를 때마다 다시 쓰고 있었다.
      **분류용 캐시를 그대로 쓸 수는 없었다** — 장당 56바이트 vs 53KB로 크기가 천 배다.
      압축하지 않고(압축은 저장을 11.3초로 만들면서 0.03GB만 줄인다) float16으로 저장하며
      (왕복 상대 오차 4.9e-4, AUROC는 여섯 자리까지 동일) memmap으로 필요한 줄만 읽는다.
      설정(백엔드·패치 크기)이 다르면 폴더가 갈려, 바꿨다 되돌려도 앞서 뽑은 것이 남는다.
- [x] **G16 작은 결함을 위한 확대** — 검출 모델을 준비하면서(H5) 미룰 수 없는 일이 됐다.
      ROI가 위치 표시용일 때는 2px 단위로도 됐지만, 검출 학습은 박스가 얼마나 정확한지에
      곧바로 좌우된다. **조작은 늘리지 않았다** — 이미 배운 드래그를 그대로 쓴다. 대충 끌고
      「지정한 영역으로 확대」를 누르면 그 둘레로 확대되고, 그 안에서 다시 그린다.
      실측: 같은 크기로 끌었을 때 확대 전 112×107 → 확대 후 25×24 (4.5배 정밀).
      화면에 **"화면 1px = 원본 2.19px"** 를 띄운다 — 그릴 수 있는 가장 작은 눈금인데
      화면만 봐서는 알 수가 없던 값이다.

(키보드 단축키는 이 도구의 사용 빈도에 비해 과하다고 판단해 후보에서 뺐다.)

## H. 영상에서 프레임 추출 (H0~H5 완료)

현장에서 학습 데이터를 모으는 방식은 대체로 **영상 촬영**이다. 이 앱은 이미지 파일만 받으므로,
자기 라인에 써 보려는 사람은 첫 단계에서 막힌다.

**설계안: [`docs/video-frame-extraction-plan.md`](video-frame-extraction-plan.md)**

핵심만 옮기면:

- 추출 간격을 감으로 정하지 않고 **공정 조건에서 계산**한다.
  `stride = floor(fps × 물체 통과 시간 / 물체당 필요 장수)`.
  같은 식을 뒤집어 **최소 요구 fps**를 내면, "이 카메라로는 애초에 안 된다"를 촬영 전에 알 수 있다.
- **데이터 누수가 가장 중요한 부분이다.** 같은 영상의 프레임을 무작위로 train/test에 나누면
  AUROC 0.99인데 현장에서 무너지는 모델이 된다. `assign_splits`에 그룹 개념이 없으므로
  **프레임 추출과 같은 단계에서 함께 고쳐야 한다.**
- OpenCV 5.0에 FFMPEG가 있어 의존성 추가는 없다. 건너뛸 프레임은 `grab()`으로 넘기고
  채택할 프레임만 `retrieve()`한다 (측정: 전부 디코딩 대비 2.5배 빠름).

**결정 완료** (설계안 §8): 1단계 추출 + 2단계 구간 라벨링 · 분할 방식은 매번 선택 ·
이번 범위는 다중 박스 라벨링까지 · 데이터는 프로젝트별 분리 · 박스는 CSV로 저장하고
내보낼 때 COCO/YOLO로 변환 · 검증은 합성 영상 + 공개 CCTV 데이터셋 + 직접 촬영 업로드.

- [x] **H0 프로젝트(작업공간) 분리** — 현장·라인마다 데이터·라벨·모델·판정 기준을 따로 관리한다.
      경로를 상수에서 **함수**로 바꿔(`config.manifest_path()` 등) 활성 프로젝트에 따라 갈리게 했다.
      기존 데이터(VisA 1.8GB 포함)는 `data/projects/default/`로 이관했다 — manifest md5가 같고
      4,584장·승격 모델 v001·판정 로그 168건이 그대로다.
      사전학습 CNN(45MB)만 프로젝트 밖 공통 보관소에 둔다.
- [x] **H1 `video.py` 코어 + 다중 박스 저장(`boxes.csv`)** — 간격 계산 3종(초당 장수 /
      공정 값 / 장면 변화), 중복 제거, 시험용 영상 생성. 박스는 한 줄이 박스 하나인 CSV로
      두고 내보낼 때 COCO/YOLO로 변환한다. 예전 단일 ROI는 박스 1개짜리로 이어받는다.
- [x] **H2 `group` 열 + 그룹 인지 분할** — H1과 함께 했다. 추출 UI를 먼저 열면 사용자가
      부풀려진 성능을 보게 되므로 누수 차단이 먼저여야 한다(설계안 §5).
      분할 방식은 매번 고르되(영상/시간/무작위), 영상 프레임이 있는데 무작위를 고르면 경고한다.
- [x] **H3 1단계 「영상에서 프레임 추출」 탭 (1차)** — 중간 점검용으로 함께 넣었다.
- [x] **H4 2단계 「영상 구간 라벨링 + 다중 박스」 탭** — 타임라인에서 구간을 끌면 그 구간의
      프레임에 라벨이 한 번에 붙는다(검사원은 프레임을 한 장씩 보지 않는다). 박스는 이미지
      위에서 여러 개 그릴 수 있고, 번호가 이미지와 목록에 함께 붙는다. 유형을 나중에 골라도
      이미 그린 박스에 반영된다. 내보내기는 CSV / COCO JSON / YOLO zip(이미지당 txt 1개 +
      `classes.txt`) 세 가지.
- [x] **H4-1 영상을 목록에서 고르기** — 경로를 통째로 타이핑하게 하면 오타 하나로 실패하고,
      무엇보다 어떤 영상이 이미 올라와 있는지 화면에서 알 수가 없다. 프로젝트 영상 폴더
      (`interim/video`)를 훑어 목록으로 주고, 프로젝트 밖에 있으면 폴더를 적어 함께 훑는다.
      시험용 영상을 만들면 곧바로 그것이 골라진 상태가 된다.
- [x] **H5 실측 + 지도학습 검출 준비** — `scripts/measure_video.py`가 아무 영상에나 같은 표를
      낸다(합성/공개 데이터셋/직접 촬영본을 같은 잣대로 비교). 측정이 **중복 판정의 결함**을
      찾아냈다: 평균 절대차는 물체 크기만으로 4배 흔들려 CCTV처럼 물체가 작으면 20초 영상에서
      1장만 남겼다. 지표를 '바뀐 칸 비율'로 바꾸고 바닥(연속 20장 버리면 1장 확보)을 깔았다.
      §7의 "grab이 2.5배 싸다"도 과장이라 1.2~1.6배로 고쳤다.
      검출은 `detection.export_yolo()`가 학습 폴더를 만들고 `scripts/train_detector.py`가
      GPU 기계에서 돌린다. 결함이 0장인 폴더는 화면과 스크립트 양쪽에서 막는다 —
      그대로 학습하면 '결함은 없다'만 배우고 지표는 훌륭하게 나온다.

**H0에서 겪은 것 두 가지** (같은 실수를 반복하지 않기 위해 기록):

1. **빈 폴더를 충돌로 봐서 216장을 뒤에 남길 뻔했다.** 앱이 시작할 때 `ensure_dirs()`가 빈
   디렉터리를 미리 만드는데, 이관이 그것을 "이미 있음"으로 보고 통째로 건너뛰었다.
   디렉터리끼리는 **안쪽 항목별로 합치도록** 고치고 회귀 테스트를 넣었다.
2. **레지스트리가 절대경로를 저장하고 있었다.** 폴더를 옮기면 승격 모델을 못 찾아 배치 추론과
   롤백이 동시에 멈춘다. 상대경로 저장으로 바꾸고 기존 행은 이관 때 고쳐 썼다.
