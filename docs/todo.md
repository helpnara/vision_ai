## 이 프로젝트가 보여주려는 것

1. **초보자도** 머신 비전으로 품질 개선을 할 수 있다
2. 모델 **개발뿐 아니라 운영관리(MLOps)까지** 가능하다

아래 항목은 전부 이 두 가지 기준으로 우선순위를 매겼다. 기능이 있느냐가 아니라
**초보자가 스스로 끝까지 갈 수 있느냐**, **운영이 돌아가는 걸 보여줄 수 있느냐**가 기준이다.

## 0. 현재 상태 진단

### 이미 목적에 맞게 되어 있는 것 (다시 손대지 말 것)

- 전문가용 손잡이를 절제했다. 3단계에서 사용자가 정하는 값은 분류기·불균형 보정·평가 분할·
  목표 재현율 넷뿐이고 전부 기본값이 잡혀 있다. 학습률·트리 깊이 같은 건 노출하지 않는다.
- **임계값을 자동으로 고른다.** 초보자가 가장 못 하는 결정을 "목표 재현율을 만족하는 것 중
  오탐 최소"라는 규칙으로 대신 처리한다.
- 다운로드 없이 합성 데이터로 전 과정을 돌릴 수 있다. 진입 장벽이 0이다.
- 4단계 구조가 실제 업무 순서(수집→라벨링→개발→운영)와 같다.

### 목적 대비 가장 큰 공백

**운영관리가 된다는 걸 보여줄 방법이 없다.** 이게 이번 검토에서 새로 나온 가장 중요한 문제다.

4단계의 드리프트 감시·성능 추이·재학습 판단은 **시간이 흐르고 데이터가 쌓여야** 의미가 생긴다.
그런데 지금 시연자가 4단계를 열면 전부 빈 화면이다. 합성 데이터로 배치 추론을 한 번 돌려도
추이가 없어서 "그래프가 하나 찍혔다"로 끝난다. 기능은 다 구현되어 있는데
**작동하는 모습을 보여줄 수가 없다.** 목적이 "운영관리도 가능함을 보여주기"인데 이건 치명적이다.

## A. 운영관리를 시연 가능하게 (최우선 · 이번 검토에서 새로 도출)

- [x] **A1. 운영 시나리오 시뮬레이터** — ✅ 완료 (`src/vision_ai/scenario.py`, 4단계 첫 탭).
      버튼 한 번으로 운영 3개월치를 재생한다.
      기능을 새로 만드는 게 아니라 **이미 만든 4단계 기능이 작동하는 모습을 보이게 하는 것**이다.

      재생 범위: 모델 승격 → 정상 운영(추론 로그 축적) → 조명 변화 주입 → PSI 경고 →
      사후 검수로 성능 변화 확인 → 재학습 신호 발생. **재학습·재승격은 시뮬레이터가 대신하지
      않는다** — 3단계 학습과 레지스트리 승격이라는 실제 기능을 그대로 쓰게 두는 편이
      "운영이 돈다"를 보여주는 데 맞다. 롤백 갈래는 A4로 남긴다.

      드리프트는 밝기/흐림 변환을 `serving.run_batch(transform=...)`에 끼워 주입한다.
      각 구간에서 "지금 무슨 일이 일어났고 왜 이 화면을 봐야 하는지"를 함께 표시한다.

      **측정으로 알게 된 것**: 환경이 변하면 미탐이 늘기 전에 **오탐이 먼저 폭증한다**
      (결함 판정 비율 6% → 34% → 83%). 원인도 정확히 짚힌다 — 조명 변화는 `gray_mean`,
      초점 저하는 `lap_p99`의 PSI가 튄다. 애초에 써 둔 시나리오 설명("재현율이 떨어진다")은
      측정과 달라 바로잡았다. 이 상황의 실제 피해는 결함을 놓치는 것이 아니라
      **사람이 볼 물량이 감당 불가로 늘어나는 것**이다.
- [x] **A2. 승격 안전장치** — 완료 (`glossary.promotion_check()`).
      D5 기준(재현율 0.95 이상, 검수량 절감률 50% 이상) 대비 점검하고, 미달이면 무엇이 왜
      미달인지 보여준 뒤 **확인 체크박스를 켜야 승격 버튼이 열린다.**
      **막지는 않는다** — 기준이 아직 승인 전 제안값이고, 비교·시연 목적으로 일부러 낮은
      모델을 올릴 수도 있다. 지표가 *없는* 것과 *미달인* 것도 구분한다.
- [x] **A3. 드리프트 원인을 평문으로** — 완료 (`glossary.FEATURE_FAMILIES`).
      특징 67개를 전부 현장 언어로 옮겼다(테스트로 누락 방지). PSI 표에 "무엇을 재는가"를

      같은 원인을 가리키는 특징이 여러 개 떠도 중복 없이 정리한다.
- [x] **A4. 롤백을 실제로 보여주기** — 완료 (`registry.rollback()`, 레지스트리 탭).
      버전을 골라 승격하는 것과 같은 동작이지만 **어느 버전으로 가야 하는지 고르는 일**이
      어렵다. 직전 서비스 버전을 찾아 한 번에 되돌린다. 시나리오 탭에도 이 갈래를 안내한다.

      고치면서 실제 결함 하나를 잡았다 — 승격 시각이 **초 단위**라 같은 초에 두 번 승격하면
      순서를 구분할 수 없어 엉뚱한 버전으로 되돌아간다. 마이크로초로 바꿨고, 그 여파로
      라벨 집계가 같은 초 라벨을 놓치는 문제도 함께 고쳤다.

앱에 표시되는 지표가 **49종**인데 대부분 숫자만 나온다. 현재 `help=` 도움말은 18개뿐이고
홈 화면에는 하나도 없다. "이 값이 높으면/낮으면 무슨 뜻이고 무엇을 해야 하는지"를 붙인다.

- [x] **C1. 품질 개선 효과를 업무 언어로** — ✅ 완료.
      환산 로직을 `evaluate.business_impact()`로 코어에 모으고 3단계 평가 화면·홈·해석

      `놓치는 결함` 건수를 항상 나란히 낸다. 둘을 같이 봐야 도입 여부를 판단할 수 있다.

      절감 없음·현장 정밀도 부족을 각각 짚어 다음에 할 일을 문장으로 낸다.
- [x] **C3. 정밀도 오해 방지** — ✅ 완료. 정밀도 캡션에 "평가 데이터 기준이라 현장과

- [x] **C4. 재현율↔정밀도 맞교환** — ✅ 완료. 임계값 조정 설명을 "한쪽만 좋게 만들 수는

### 도움말 배치 방식 (먼저 결정할 것)

| 방식 | 장점 | 단점 |
|---|---|---|
| `?` 아이콘 (`help=`) | 화면이 깔끔 | 눌러야 보여서 초보자는 그냥 지나침 |
| 지표 옆 캡션 | 바로 보임 | 화면이 길어짐 |
| 상단 접이식 "이 화면 읽는 법" | 절충 | 지표와 설명이 떨어져 있음 |

**혼합안으로 확정** — 핵심 지표(`primary=True`)는 캡션으로 바로 보이게, 부가 설명은 `?`에 둔다.

(전에는 정밀도가 3단계·홈·문서에서 각각 다른 문장으로 설명되고 있었다.)

## F. 기술 작업 (성능·검증)

목적이 "초보자도 할 수 있음을 보여주기"이므로 **성능 개선보다 A~C가 먼저다.**
지금 성능(평균 AUROC 0.830)으로도 "검수량 54% 절감"이라는 이야기는 성립한다.

- [x] **성능 개선 시도** — 사전학습 CNN 측정 완료(4.6). 소폭 개선이나 위치 정확도가
      나빠져 선택 기능으로만 둔다. 벤치마크 수준(0.95)을 원하면 PatchCore 계열로
      **방법 자체를 바꿔야 한다** — 특징만 갈아끼워서 되는 일이 아니었다.
- [ ] **재현율 목표 미달 해소** — 홀드아웃 평균 0.925 (제안 기준 0.95). pcb4가 0.840으로 가장 낮다.
- [x] **결함 유형 라벨링** — 흐름 확인 및 유형 파악 완료 (설계 문서 4.7).

## G. 사용성 (쓰면서 계속 발굴)

기능이 다 있어도 화면이 불편하면 계속 쓰지 않게 된다. **실제로 써 보다가 걸린 것을 그때그때
여기에 적고 처리한다.** 아래는 그 첫 회차다.

- [x] **G1 글자 크기** — 기본 테마는 발표 슬라이드에 가까워서 h1이 44px, 지표 값이 36px였다.
      1440×900 화면에 진행 순서 항목이 한 개밖에 안 들어왔다. `.streamlit/config.toml`의
      테마 옵션으로 h1 25.5px / 지표 값 22.5px까지 줄여 같은 화면에 네 개가 들어온다.
      CSS 주입이 아니라 Streamlit이 공식 지원하는 설정이라 버전 업에 안전하다.
- [x] **G2 여백** — 본문 상단 90px·하단 150px, 구분선 위아래 각 2rem이 스크롤을 한 번 더
      만들고 있었다. 상단 37.5px·하단 45px, 구분선 1rem으로 줄였다 (`src/vision_ai/ui.py`).
- [x] **G3 메뉴 레일 모드** — 기본 사이드바는 접으면 통째로 사라져서 "지금 몇 단계인지"를
      잃어버린다. Claude Console처럼 아이콘만 남기는 74px 레일을 만들었다. 접은 상태에서도
      현재 페이지에 배경 표시가 남고, 아이콘에 마우스를 올리면 단계 이름이 뜬다.
      기본 메뉴(`position="hidden"`) 대신 `st.page_link`로 직접 그린다.

- [x] **G3-1 접기 버튼 중복 제거** — 기본 « 버튼(패널 통째로 숨김)과 레일 토글이 같은
      자리에 나란히 있어 기능이 겹쳤다. 넓은 화면에서는 기본 버튼을 숨기고 그 자리에 레일
      토글을 올려 **버튼을 하나로** 만들었다. 다만 폰에서는 사이드바가 본문을 덮으므로
      "완전히 치우기"가 맞아, 640px 이하에서는 반대로 기본 버튼을 남기고 레일 토글을 숨긴다.
      어느 폭에서든 화면에 보이는 접기 버튼은 하나뿐이다.
- [x] **G4 표 가독성** — 데이터셋 카탈로그 표가 8열이라 좁은 화면에서 폭에 맞추려다 글자가
      뭉개졌다. ⭐ 열을 이름 앞으로 합쳐 7열로 줄이고, 열마다 폭을 지정해 **찌그러뜨리는 대신
      가로 스크롤**이 생기게 했다. 이름 열은 고정(pinned)해 스크롤해도 어느 줄인지 잃지 않는다.
      설명이 필요한 열(일상 적합도·상업적 이용·폴더 구조·key)에는 열 도움말을 달았다.
- [x] **G5 탭 개수** — 4단계 탭 7개가 좁은 화면에서 가로 스크롤로 밀려 뒤쪽 탭이 "없는 것"처럼
      보였다. 줄바꿈으로 바꿔 **1000px·768px·390px 모두에서 7개가 전부 보이는 것**을 확인했다.
- [x] **G6 모바일/태블릿** — 원인은 `initial_sidebar_state="expanded"`였다. 390px 화면에서
      300px 사이드바가 열린 채로 떠서 본문에 90px만 남았다. `"auto"`로 바꿔 좁은 화면에서는
      접힌 채로 열리게 했고, 본문 좌우 여백도 900px 이하에서 75px → 15px로 줄였다.
      1440·1024·768·390px에서 확인.
- [x] **G7 다크 모드** — `base = "light"` 고정을 풀어 브라우저·OS 설정을 따라가게 했다.
      `primaryColor`가 강조색이자 기본 버튼 **배경**이라 밝히기만 하면 흰 글씨가 안 읽힌다.
      실측으로 절충점을 잡았다: `#2f6fe4` (흰 글씨 4.65 : 배경 4.06, 둘 다 통과).
      링크는 글자색이라 제약이 달라 따로 `#7dd3fc`(대비 11.3). 6개 화면 × 밝게/어둡게
      12조합에서 예외 없이 렌더링되는 것을 확인했다.

- [x] **G8 표 도움말 일관성** — 지표를 지표 카드에서는 캡션으로 설명해 놓고 표에서는 맨 이름만
      내보내고 있었다. 열 도움말도 용어 사전(`glossary.column_help`) **한 곳에서** 나오게 하고,
      `ui.table_columns()`가 열 이름을 보고 자동으로 붙인다. 뜻이 분명한 열(version, created_at)은
      건드리지 않는다 — 다는 것이 다 도움이 되지는 않는다. tp/fp/fn/tn 같은 약어와 실험 기록의
      run_id·threshold, 드리프트의 baseline_mean·shift_sigma에도 설명을 달았다.
- [x] **G9 폰에서의 표** — 390px에서 표는 가로 스크롤로 볼 수는 있지만 한 줄을 읽으려면 좌우로
      오가야 해서 실제로는 안 보게 된다. `ui.responsive_table()`이 표와 카드를 둘 다 그려 놓고
      CSS로 하나만 보인다(서버는 브라우저 폭을 모른다). 줄 수가 적은 표에만 쓴다 — 로그처럼 긴
      표에 쓰면 쓰지도 않을 카드를 수백 개 그리게 되므로 `card_limit`으로 막았다.
- [x] **G11 화면 여는 속도** — G8을 확인하다 발견했다. 3단계 베이스라인 탭이 **버튼을 누르기도
      전에** 라벨된 이미지 전량의 특징을 뽑고 있었다(장당 16ms × 4,584장). 화면 하나 여는 데
      **112초**가 걸렸고, 탭을 누를 때마다 처음부터 다시 걸려 뒤쪽 탭은 사실상 열리지 않았다.
      장수는 라벨 표만 세면 알 수 있으므로 특징 추출을 버튼 뒤로 미뤘다 — **112초 → 0.8초.**
      6개 화면 모두 10초 안에 열리는지 테스트로 잠갔다.

> G11은 "쓰면서 발굴한다"가 왜 필요한지 보여주는 사례다. 코드만 읽어서는 드러나지 않았고,
> 기능 검증(G8)을 하려고 실제로 탭을 눌러보다 걸렸다.

- [x] **G12 진행 표시** — 막대만 채우면 화면이 멈춘 것처럼 보여 사람은 새로고침을 누른다.
      **왜 오래 걸리는지**를 먼저 말하고(`이미지 4,584장에서 각각 67개 값을 계산합니다`),
      진행하면서 **남은 시간**을 실측 속도로 갱신한다(`특징 추출 중 100/4,584 · 남은 시간 약 45초`).
      처음 12건은 편차가 커서 값을 못 믿으므로 그전에는 건수만 보여준다. 끝나면 실제로 걸린
      시간을 남긴다(`1분 28초 걸림`).
- [x] **G13 특징 캐시** — 한 번 계산한 특징을 `artifacts/cache/`에 남긴다.
      **이미지 단위**로 남기는 것이 핵심이다 — 집합 단위로 캐싱하면 이미지를 10장 추가하는
      순간 전체가 무효가 되지만, 이미지 단위면 늘어난 10장만 계산한다.
      실측 **144초 → 0.1초** (동일 결과 확인, 캐시 파일 4,584장에 1.0MB).
      파일이 바뀌었거나(수정 시각·크기) 특징 정의가 바뀌면 자동으로 버린다.
      설정 화면에 현황과 비우기를 뒀다.

## H. 영상에서 프레임 추출 (설계 검토 중)

현장에서 학습 데이터를 모으는 방식은 대체로 **영상 촬영**이다. 이 앱은 이미지 파일만 받으므로,
자기 라인에 써 보려는 사람은 첫 단계에서 막힌다.

**설계안: [`docs/video-frame-extraction-plan.md`](video-frame-extraction-plan.md)**

핵심만 옮기면:

- 추출 간격을 감으로 정하지 않고 **공정 조건에서 계산**한다.
  `stride = floor(fps × 물체 통과 시간 / 물체당 필요 장수)`.
  같은 식을 뒤집어 **최소 요구 fps**를 내면, "이 카메라로는 애초에 안 된다"를 촬영 전에 알 수 있다.
- **데이터 누수가 가장 중요한 부분이다.** 같은 영상의 프레임을 무작위로 train/test에 나누면
  AUROC 0.99인데 현장에서 무너지는 모델이 된다. `assign_splits`에 그룹 개념이 없으므로
  **프레임 추출과 같은 단계에서 함께 고쳐야 한다.**
- OpenCV 5.0에 FFMPEG가 있어 의존성 추가는 없다. 건너뛸 프레임은 `grab()`으로 넘기고
  채택할 프레임만 `retrieve()`한다 (측정: 전부 디코딩 대비 2.5배 빠름).

**착수 전 답이 필요한 것** (설계안 §8): 배치(1단계 추출 + 2단계 구간 라벨링인지),
그룹 단위(영상인지 물체인지), 기존 manifest 호환, 검증용 영상 확보 방법.
