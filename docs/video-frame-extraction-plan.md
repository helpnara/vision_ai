# 영상에서 프레임 추출 — 설계안 (H)

> 상태: **§8 결정 완료 · H0(프로젝트 분리) 구현 완료.** H1부터 이어서 진행한다.
> 작성 근거: 이 저장소의 현재 코드(`storage.MANIFEST_COLUMNS`, `labeling.assign_splits`,
> `guide.MIN_NORMAL_FOR_ANOMALY`)와 이 환경에서 직접 측정한 값(§7).

## 1. 왜 필요한가

현장에서 학습 데이터를 모으는 방식은 대체로 **영상 촬영**이다. 라인 위 카메라는 영상으로
돌고, 검사원이 나중에 돌려 보며 결함 구간을 짚는다. 사진을 한 장씩 찍어 모으는 경우는
드물다. 그런데 이 앱은 지금 **이미지 파일만** 받는다(폴더 임포트 · 업로드 · 합성 생성).

즉 이 기능이 없으면, 이 도구를 자기 라인에 써 보려는 사람은 **첫 단계에서 막힌다.**
"초보자도 머신 비전으로 품질 개선을 할 수 있다"를 보이려는 프로젝트에서 이건 큰 공백이다.

## 2. 이 설계의 중심 질문 — "몇 장을 뽑아야 하는가"

영상은 프레임이 넘쳐난다. 30fps로 10분이면 18,000장이다. 그래서 **전부 뽑는 것은 답이
아니고**, 감으로 "10프레임마다" 정하는 것도 답이 아니다. 두 방향에서 동시에 틀릴 수 있다.

| 너무 적게 뽑으면 | 너무 많이 뽑으면 |
|---|---|
| 결함이 있는 물체가 **한 장도 안 찍힌다** | 라벨링 비용이 폭발한다 (사람이 봐야 할 장수) |
| 찍혀도 흔들리거나 가려진 한 장뿐이라 못 쓴다 | 거의 같은 이미지라 **정보량은 늘지 않는다** |
| | 인접 프레임이 train/test에 나뉘어 **성능이 부풀려진다** (§5) |

그래서 추출 간격을 **공정 조건에서 계산**한다. 사용자가 입력할 값은 세 가지다.

- `fps` — 영상 메타데이터에서 자동으로 읽는다 (사용자 입력 아님)
- `t_visible` — 물체 하나가 화면을 지나가는 시간(초).
  라인 속도 `v`(m/s)와 카메라 시야 길이 `L`(m)을 알면 `t_visible = L / v`
- `k` — **물체당 확보하고 싶은 장수** (기본 3: 흔들림·가림 대비 여유)

### 2.1 추출 간격

```
물체 하나가 찍히는 프레임 수  = fps × t_visible
추출 간격 stride (프레임)     = max(1, floor(fps × t_visible / k))
초당 추출 장수                = fps / stride
예상 추출 장수 n              = ceil(전체 프레임 수 / stride)
```

**예시**: `fps=30`, 시야 `L=0.30m`, 라인 속도 `v=0.5m/s`
→ `t_visible = 0.6초` → 물체당 18프레임 → `k=3`이면 `stride = 6` (초당 5장)
→ 10분 영상에서 **3,000장** (18,000장 전부 뽑는 것 대비 1/6)

### 2.2 되짚어 보는 계산 — 이 촬영이 애초에 가능한가

이 계산의 진짜 값어치는 숫자를 내주는 데 있는 게 아니라, **불가능한 조건을 미리 알려주는
데** 있다. 같은 식을 뒤집으면 최소 요구 fps가 나온다.

```
최소 요구 fps = k / t_visible
```

`v=5m/s`처럼 라인이 빠르면 `t_visible = 0.06초`, `k=3`을 채우려면 **50fps**가 필요하다.
30fps 카메라로는 물체당 1.8프레임이라 **애초에 목표를 못 채운다.** 화면은 이때
"지금 카메라로는 물체당 1.8장뿐입니다 — 라인을 늦추거나 고속 카메라가 필요합니다"라고
말해야 한다. 이건 추출 설정이 아니라 **촬영 계획의 문제**이고, 프레임을 뽑기 전에 알아야
비용을 아낀다.

### 2.3 모델이 요구하는 최소 장수와 잇기

"몇 장이 필요한가"의 다른 절반은 **모델 쪽 요구**다. 이 프로젝트에는 이미 기준이 있다.

| 방식 | 최소 장수 | 근거 (코드) |
|---|---|---|
| 이상탐지 (위치별 분포) | 정상 **15장** 초과 | `guide.MIN_NORMAL_FOR_ANOMALY` = 패치 특징 14차원 + 1 |
| 베이스라인 (지도학습) | 결함 **10장** 이상 | `guide.MIN_DEFECT_FOR_BASELINE` |

추출 화면은 예상 추출 장수를 이 기준과 나란히 보여준다.
*"이 영상에서 약 3,000장이 나옵니다. 이상탐지 학습에 필요한 정상 최소치(15장)는 넘지만,
결함 구간을 지정하지 않으면 결함은 0장입니다."*
숫자만 던지지 않고 **다음에 무엇을 해야 하는지**까지 잇는 것이 기존 `guide` 모듈의 방식이고,
여기서도 같게 간다.

### 2.4 입력 모드 세 가지

라인 속도를 모르는 사람도 있다. 계산을 강요하면 그 자리에서 막힌다.

| 모드 | 입력 | 언제 |
|---|---|---|
| **A. 공정 값으로 계산** (권장) | 시야 길이 · 라인 속도 · 물체당 장수 | 컨베이어 등 조건을 아는 경우 |
| **B. 직접 지정** | "초당 n장" 또는 "N프레임마다" | 감이 있거나 조건을 모르는 경우 |
| **C. 장면이 바뀔 때만** | 유사도 임계값 | 정지 구간이 길거나 비정기 촬영 |

A를 기본으로 하되 **B로 언제든 넘어갈 수 있어야 한다.** A에서 계산된 값이 B의 초기값으로
들어가면, 계산을 이해 못 해도 결과는 쓸 수 있다.

## 3. 중복 제거

균등 추출만으로는 부족하다. 컨베이어가 멈춘 구간에서는 같은 이미지가 쏟아진다.

- 프레임을 작게 줄여(예: 32×32 그레이스케일) 직전 채택 프레임과의 **평균 절대 차이**를 본다
- 임계값 미만이면 버린다
- 이 앱의 67차원 특징을 쓰는 것은 과하다 — 버릴 프레임에 쓰기엔 비싸다

이건 **모드 C의 알맹이이자, A·B에도 함께 거는 안전장치**로 둔다.

## 4. 품질 필터

영상 프레임은 정지 이미지보다 품질이 나쁘다 — 모션 블러, 압축 아티팩트, 노출 변동.
이 앱에는 이미 `quality` 모듈과 기준값(선명도 100, 밝기 40/215)이 있다. 추출 시점에 걸어
흐린 프레임을 자동으로 제외하고, **몇 장이 왜 빠졌는지 화면에 남긴다**(조용히 버리면
"왜 3,000장이라더니 2,700장이지?"가 된다).

> 주의: 기준값은 이 데이터로 검증한 값이 아니다 (`glossary.ARBITRARY["quality"]`).
> 영상 프레임은 전반적으로 정지 이미지보다 흐리므로, **기본값을 그대로 쓰면 과하게 버릴 수
> 있다.** 처음에는 필터를 끈 채 분포를 먼저 보여주고 사용자가 기준을 정하게 하는 편이 낫다.

## 5. 데이터 누수 — 이 설계에서 가장 중요한 부분

**같은 영상에서 뽑은 프레임은 서로 매우 비슷하다.** 이것을 무작위로 train/test에 나누면,
테스트 세트에 학습 이미지와 거의 같은 장면이 들어간다. 결과는 **AUROC 0.99인데 현장에서
무너지는 모델**이다. 영상 데이터로 넘어갈 때 가장 흔하고 가장 비싼 실수다.

현재 `labeling.assign_splits`는 **카테고리 × 라벨로 층화**할 뿐 그룹 개념이 없다.
영상을 받아들이려면 여기를 반드시 함께 고쳐야 한다.

```
manifest에 group 열 추가 (영상 id, 더 좋게는 물체 id)
        ↓
assign_splits: 같은 group은 통째로 같은 split에
        ↓
2단계 분할 화면: "영상 단위로 나눔" 표시 + 왜 그래야 하는지 한 줄
```

**이 기능을 붙이면서 분할을 그대로 두는 선택지는 없다.** 프레임 추출만 먼저 넣으면
사용자는 부풀려진 성능을 보게 되고, 그건 이 도구가 하지 말아야 할 일이다.
그래서 §9의 단계 구분에서 **그룹 분할을 프레임 추출과 같은 단계에 넣었다.**

## 6. 어디에 넣을 것인가 — 1단계인가 2단계인가

요청은 "라벨링 단계에 추가"였다. 다만 이 앱의 구조에서 보면 나눠 볼 필요가 있다.

| 하는 일 | 파이프라인상 위치 | 이유 |
|---|---|---|
| 영상 → 프레임 추출 → manifest 등록 | **1단계 (데이터 수집)** | manifest에 넣는 행위가 곧 "수집"이다. 폴더 임포트·업로드와 같은 성격 |
| 영상 타임라인에서 결함 **구간** 지정 → 프레임 일괄 라벨 | **2단계 (라벨링)** | 라벨을 붙이는 행위 |

**구간 라벨링이 실무 흐름에 더 가깝다고 본다.** 검사원은 프레임을 한 장씩 보지 않는다.
영상을 돌려 보며 "3분 12초부터 3분 20초까지 불량"이라고 짚고, 그 구간의 프레임 전체에
결함 라벨이 붙는 방식이다. 한 장씩 라벨하면 3,000장을 한 장씩 봐야 한다 — 영상을 쓰는
이유가 사라진다.

→ **제안: 두 곳 모두.** 1단계에 「영상에서 프레임 추출」 탭, 2단계에 「영상 구간 라벨링」 탭.
다만 §8에서 이 배치를 확인받고 싶다.

### 6.1 구간 지정은 이미 있는 방식을 그대로 쓴다

2단계 결함 위치 지정은 G15에서 **이미지 위 드래그**로 바뀌었다(`ui.roi_picker`). 타임라인에서
시간 구간을 끄는 것도 같은 도구로 된다 — Vega-Lite 구간 선택을 x축(시간) 하나만 쓰도록
바꾸면 그만이다. 새로 만들 것이 없고, 사용자가 배우는 조작도 하나다.

```
결함 위치 지정 : 이미지 위에서 x·y 두 축을 끈다   (구현됨)
결함 구간 지정 : 타임라인에서 x 한 축만 끈다      (같은 도구, encodings=["x"])
```

## 7. 기술 제약 (이 환경에서 측정)

OpenCV 5.0.0, FFMPEG **YES** — 별도 의존성 추가 없이 영상을 읽을 수 있다.

720p / 600프레임 합성 영상 기준:

| 방식 | 시간 |
|---|---|
| `grab()`만 (디코딩 생략) 600프레임 | 0.20초 |
| `read()` 전부 디코딩 600프레임 | 0.49초 |
| `stride=15`로 40장 추출 (`grab` 건너뛰기 + 필요할 때만 `retrieve`) | 0.20초 |

→ **건너뛸 프레임은 `grab()`으로 넘기고, 채택할 프레임만 `retrieve()`로 디코딩한다.**
전부 디코딩하는 것보다 2.5배 싸다.

> 이 숫자는 **단순한 합성 영상 기준이라 낙관적이다.** 실제 촬영본은 압축률이 높아 디코딩이
> 더 비싸다. 구현 후 실제 영상으로 다시 재야 한다.

그 밖의 제약:

- **메모리** — 프레임을 모아 뒀다 저장하면 안 된다. 순차 처리 + 즉시 저장.
  1080p 프레임 하나가 6MB(비압축)이고 3,000장이면 18GB다.
- **배포 환경** — Streamlit Cloud는 업로드 200MB 제한에 컨테이너가 일회성이다.
  VisA와 같은 이유로 **영상 기능은 로컬 실행 전용**으로 본다. 배포본에서는 안내만 띄운다.
- **진행 표시** — 10분 영상 처리는 오래 걸린다. G12에서 만든 `ui.Progress`를 그대로 쓴다.
- **원본 영상** — 복사하지 않고 경로만 기록한다 (폴더 임포트와 같은 철학).

## 8. 확정된 결정

| 항목 | 결정 |
|---|---|
| 배치 | **1단계 추출 + 2단계 구간 라벨링** (§6 제안대로) |
| 분할 방식 | **매번 선택** — 영상 단위 / 시간 순서 / 무작위. 기본값은 영상 단위이고, 영상 데이터가 있는데 무작위를 고르면 성능이 부풀려진다고 경고한다 |
| 이번 범위 | **다중 박스 라벨링까지.** 객체 탐지 모델 학습은 이후 단계 |
| 클래스·데이터 관리 | **프로젝트(작업공간)별로 분리** → H0에서 구현 완료 |
| 박스 저장 형식 | **내부 CSV, 내보낼 때 COCO/YOLO로 변환** |
| 검증용 영상 | 지금은 **합성 영상 + 공개 CCTV 데이터셋**, **직접 촬영 업로드도 구현** |
| 이후 계획 | 객체 탐지 모델은 고성능 시스템이 필요하므로 준비되면 **로컬호스트**로 진행 |

### 확정에 따라 달라진 것

* **CCTV가 데이터 공급원이다.** §2의 추출 간격 계산은 컨베이어 전제(일정한 라인 속도)라
  CCTV에는 그대로 맞지 않는다. 물체가 멈춰 있기도 하고 속도도 제각각이라 `t_visible`을
  정할 수 없다. **CCTV에서는 §3의 장면 변화 기반 추출이 주가 되어야 한다.**
  공정 값 계산(모드 A)은 컨베이어가 있는 경우의 선택지로 남긴다.
* **단일 ROI는 박스 1개짜리 다중 박스로 취급**해 그대로 이어받는다. 기존 라벨을 잃지 않는다.

## 9. 단계 구분 (착수 시)

| 단계 | 범위 | 왜 이 순서인가 |
|---|---|---|
| ~~**H0**~~ | ~~프로젝트(작업공간) 분리~~ | ✅ 완료 — 나중에 넣으면 쌓인 데이터를 전부 이관해야 했다 |
| **H1** | `video.py` 코어 + 다중 박스 저장(`boxes.csv`) | UI 없이 테스트 가능한 부분부터 |
| **H2** | `group` 열 + 그룹 인지 분할 (`assign_splits`) | **H3보다 먼저.** 누수를 막을 준비가 된 뒤에 데이터를 들여야 한다 (§5) |
| **H3** | 1단계 「영상에서 프레임 추출」 탭 | 계산 근거·예상 장수·최소 요구 fps 경고 포함 |
| **H4** | 2단계 「영상 구간 라벨링」 탭 | 구간 지정 → 프레임 일괄 라벨 |
| **H5** | COCO/YOLO 내보내기 + 실제 촬영본으로 측정 | 학습 준비 · §7의 숫자를 실제 영상으로 갱신 |

## 10. 이 설계가 하지 않는 것

- **객체 추적(tracking)** — 물체 하나를 프레임 간에 이어 붙이는 일. 물체 단위 그룹핑에
  필요하지만 범위가 크게 늘어난다. 우선 영상 단위 그룹으로 시작한다.
- **영상 자체를 입력으로 쓰는 모델** — 시간 정보를 쓰는 모델(예: 프레임 간 변화로 판정)은
  다른 접근이다. 여기서는 어디까지나 **영상을 이미지 공급원으로** 본다.
- **실시간 스트림** — RTSP 등 라이브 입력. 파일 단위 처리부터 한다.
